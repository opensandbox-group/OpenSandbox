## Summary

[OSEP-0026](0026-resource-oversubscription-accounting-for-fast-sandbox.md) (implemented) established the server↔FastPath resource-accounting contract for Fast Sandbox: effective machine shapes are forwarded as nominal limits, requests stay pool-derived, and host cgroups enforce per-sandbox budgets. That contract accounts the *worst case*; it cannot see what a running fleet actually holds. The [ROADMAP](../ROADMAP.md) carries the explicitly unplanned remainder of the same scope: *"Fast Sandbox ultra-high density and memory oversubscription — define the deployment and resource model for packing very high sandbox density per Fastlet Pod, including a memory oversubscription model with bounded overcommit, reclaim, and OOM-isolation guarantees."*

This OSEP proposes that operational half on top of the implemented ledger: **working-set-aware admission** (dual pressure signals + a declared floor/cap elastic memory tier + a per-node aggregate invariant), a **reclaim layer** (free-page-reporting baseline + managed balloon with measured ordering), **OOM isolation** (`deflate_on_oom`), **density observability**, and explicit **escape hatches**. It is Firecracker-runtime-shaped but touches no VMM internals — everything rides existing Firecracker APIs/config that upstream already ships ([PR #114](https://github.com/opensandbox-group/fast-sandbox/pull/114) landed default free-page reporting; the balloon device and `deflate_on_oom` are long-standing). Every layer is flag-gated and individually rollback-safe; `LegacySlot` and current `ResourceAware` behavior is preserved bit-for-bit when all switches are off.

## Motivation

One of the three pieces named in the ROADMAP row — bounded overcommit — is implemented today as a model; the other two exist only as unmanaged mechanisms.

**What exists.** `ResourceAware` pools ([tracking issue #115](https://github.com/opensandbox-group/fast-sandbox/issues/115), [design doc](https://github.com/opensandbox-group/fast-sandbox/blob/main/docs/design/resource-aware-overcommit-placement.md), fast-sandbox PR #122/#162, and the server-side forwarding contract in [OSEP-0026](0026-resource-oversubscription-accounting-for-fast-sandbox.md)) deliver **bounded overcommit**: per-sandbox limits, pool-owned overcommit ratios, a per-Fastlet commitment ledger, pressure-gated admission at the slot boundary, and host cgroup enforcement. That layer is implemented and this proposal builds on it rather than re-proposing it.

**What is missing.** The design doc's own non-goals exclude exactly the remaining ROADMAP scope: it does not dynamically react to *observed* usage, does not treat RSS as the commitment charge, and explicitly excludes "reclaiming, pausing, migrating, or evicting existing Sandboxes." Concretely, two density problems remain open:

1. **The nominal-admission ceiling.** Admission charges a limit-derived request (limit / static ratio). But a running idle 1 vCPU / 512 MiB microVM actually holds ~17.8 MB of host memory — roughly **3.5% of its nominal charge**. The static ledger therefore cannot express how much headroom a *reclaimed* fleet actually has, and operators compensate by keeping memory overcommit ratios conservative (e.g. 1.25 in the design doc example). The gap between charged and resident memory is the single largest untapped density reserve, and today nothing measures it, admits against it, or protects it.
2. **No reclaim loop.** Long-lived Firecracker sandboxes do not return freed memory: guest free pages and cold file cache keep consuming host memory between tool calls. Without an observe → reclaim → verify → admit loop, "idle" is indistinguishable from "busy" at the host level, and density is capped by the worst-case sum of limits rather than the working set.

### Goals

- A working-set-aware admission signal that complements the static commitment ledger, gated behind pool policy and defaulted off.
- A declared **floor/cap memory tier** ("elastic" memory), isomorphic to Kubernetes Burstable request/limit semantics, declared at create time (Firecracker cannot hot-add memory and the balloon can only shrink below the initial spec — elasticity is structurally create-time-only). In this OSEP the tier is **pool-policy-resolved** at create time (a per-Pool floor/cap default tier, with `cap` from the template's recorded machine shape) — no public API surface is involved; a caller-supplied floor would require an additive public field and is future work.
- A node-level aggregate invariant (Σ declared caps ≤ 80% of node memory) that makes "everyone inflates fully at once" physically safe by construction.
- A reclaim layer with measured ordering guarantees, so tightening pressure never converts into guest OOM kills.
- Observability sufficient to operate density as an SLO (eviction/OOM rate, reclaim effectiveness, residency).
- Preserve `LegacySlot` and current `ResourceAware` behavior bit-for-bit when all new switches are off.

### Non-Goals

- **No VMM-internal changes.** Everything rides shipped Firecracker APIs/config (balloon device, free-page reporting, `deflate_on_oom`, snapshot paths). No Firecracker forks, no patched kernels beyond what PR #114 already bakes.
- **No network-plane work.** Ingress gateway, egress, and network policy are separate ROADMAP rows with their own proposals.
- **No concrete scheduler implementation.** The Σ-invariant is a placement *filter* exposed to the existing FastPath placement; Kubernetes bin-packing and node autoscaling stay external, consistent with the ResourceAware non-goals.
- **No public API surface change.** The elastic tier is pool-policy-declared (a floor/cap default tier plus the template's recorded machine); a caller-facing floor/cap field would touch OpenAPI/spec/SDKs and is explicitly future additive work, not part of this OSEP.
- **No dynamic overcommit-ratio auto-tuning.** Ratios remain static pool policy (existing non-goal). The working-set layer reacts to pressure; it does not rewrite the ledger's ratios.
- **No host swap as capacity.** (Existing non-goal, kept.) An optional *guest-side* swap on platform storage remains a per-sandbox emergency opt-in and never enters node capacity accounting.
- **No eviction/pause/migrate of existing sandboxes as a reclaim mechanism.** Reclaim means free-page reporting, balloon tightening, and page-cache reclaim. Lifecycle automation is a separate ROADMAP row.
- **No KSM-on-restore dependency** (structurally unavailable, E6).

## Proposal

Four independent layers, each individually flag-gated and individually rollback-safe. The static `ResourceAware` ledger stays the accounting boundary; every layer below is additive to it.

### Layer 1 — Admission: working-set-aware gating

- **Dual signal, fixed roles.** The *density* signal is the sandbox parent cgroup's CPU pressure, read per-Fastlet: the gate keys off **`cpu.pressure some`** (partial stalls) above a flag-gated threshold with hysteresis, with `cpu.pressure full` as a corroborating secondary only — on a multi-task parent cgroup at least one task is almost always running, so `full` stays 0 even while the host saturates and cannot serve as the gate by itself. The calibration base: idle-neighbor probe degradation stayed ≤ 1.04× (E2) with `PSI cpu some avg60` ≤ 6.7% in the 30%-busy mix; full CPU saturation was not exercised in those runs, so the `some` threshold is an explicit Stage 2 calibration deliverable (asserted by the saturation-window acceptance test below), not a measured constant. The *memory* red line is watched at **two levels**: node `MemAvailable` bands (E7) and each Fastlet parent cgroup's own memory headroom — enter when `memory.current` reaches `memory.max` minus a flag-gated reserve sized so the freeze lands before the hard limit/OOM, with cgroup `memory.pressure some` (60 s window) as the corroborating signal and exit on a higher recover reserve under the same hysteresis/batching discipline as the node branch. A limit-only pool can exhaust its aggregate cgroup budget well before the node gets hot, and must freeze admission on its own headroom rather than wait for node `MemAvailable` to move. Node bands have explicit enter/exit semantics: enter when `MemAvailable` falls below the enter threshold (default 15%, flag-gated), tiers execute in order (freeze new inflates → global tighten → enforce floors), and exit requires `MemAvailable` to rise above a separate, higher recover threshold — hysteresis, both flag-gated — with re-opening batched on the `Retry-After` cadence so a node oscillating around the threshold cannot flap balloon/throttle state. Both signals gate only *new* admission; neither re-ranks nor evicts placed sandboxes (that stays a non-goal, matching the existing design doc).
- **Declared floor/cap memory tier.** Per-sandbox memory becomes `resources.memory = {floor, cap}` (optional; absent = today's limit-only semantics), resolved at create time from pool policy (a per-Pool floor/cap default tier) plus the template's recorded machine shape for `cap`, carried on the internal FastPath `CreateSandboxRequest.resources` extension. Semantics are deliberately Kubernetes-Burstable-isomorphic: `cap` = guest physical address space, charged at admission; `floor` = guaranteed memory under red-line events, never reclaimed below. Firecracker structurally forces this to be create-time-only (no memory hotplug; balloon may only shrink below the initial spec), which we validated and consider a feature: it keeps the guest hard boundary at the declared cap, with guest-kernel-autonomous OOM inside (host- and neighbor-invisible), consistent with today's enforcement model. Because `cap` *is* the guest address space, validation pins `cap == machine memory`: on restore-based creates that is the snapshot's recorded machine, and a larger cap is rejected (it would only consume invariant budget for address space the guest can never use; resizing means rebuilding the template).
- **Node invariant (declared-cap pools).** For pools that enable the elastic tier, placement additionally enforces **Σ declared caps ≤ 80% of node memory** per Fastlet host (E9). The sum is **per host across all sandboxes and pools**, not per enabling pool: co-located limit-only pools' reservations and the host's non-sandbox baseline count against the same budget — otherwise a shared node could pass the elastic filter and still over-commit at full inflation. Where exclusive-host placement is not available, co-located workloads must be charged at a **bounded reservation** — their declared limits or a fixed reservation — never at measured current usage: a neighbor can hold low RSS while elastic caps are placed and then grow within its own limit, which would make a measured charge transient and the invariant unsound. If a bounded reservation cannot be established for every co-resident workload, the guarantee does not hold on that host and declared-cap pools must use dedicated hosts. The fence is **host-wide and continuous**: once a host holds cap reservations, every subsequent sandbox placement onto that host — from any pool — traverses the same budget, and non-sandbox Kubernetes placements must be kept off such hosts (taint/dedicated nodes) or charged a bounded reservation at scheduling time; a filter scoped to the enabling pool alone would let later creates invalidate simultaneous full inflation. The filter is also **paired with the Fastlet's aggregate memory cgroup envelope**: today's shared sandbox parent cgroup is sized `max(defaultRequest × maxSandboxesPerPod, defaultLimit)` (the [OSEP-0026](0026-resource-oversubscription-accounting-for-fast-sandbox.md)/PR #162 enforcement shape), so a cap sum that passes the physical-memory filter can still cgroup-OOM VMMs at full inflation before host memory is touched — enabling the elastic tier must check/resize that aggregate `memory.max` so Σ caps physically fit inside it (or provision declared-cap hosts from the invariant), and the Test Plan exercises full inflation at that cgroup boundary. This invariant is independent of the per-Pool commitment ledger: the ledger answers "does this Pod have budget", the invariant answers "can this node survive simultaneous full inflation". We propose the invariant as a placement filter, not a scheduler change. Where a pool does not declare caps, the node's memory protection is the red line plus `deflate_on_oom` — the posture the 4000-sandbox evidence ran under — and no hard simultaneous-full-inflation guarantee is claimed for that profile.
- **Tradeoff.** Dual signals can disagree (CPU idle, memory hot). We resolve by roles (CPU gates density, memory gates safety) rather than a combined score — no tuning surface, no hidden weights.

### Layer 2 — Reclaim: FPR baseline, balloon actuator, measured ordering

- **FPR is the default-on baseline** (already landed via PR #114 for newly built snapshots). Two additions: fold the measured ~7 MB/sandbox idle cost into the existing fixed per-runtime overhead budget (E3), and verify/force `deflate_on_oom = true` in the bake path (E5 — it is the only tier that requires zero policy).
- **Balloon is the managed actuator**, driven only under the red-line state machine, never as a working-set probe (E4). Control channel must be **host-initiated**: in our validation, guest→host vsock connects (host-side listeners in init/cell/pod netns) were unreliable (connection RSTs); the working pattern is the Firecracker UDS proxy with a guest-agent as the vsock *server*. This is an implementation constraint worth codifying here so implementations don't rediscover it.
- **Ordering rules, promoted from measured failures (E8):**
  1. Throttle (CPU/IO) **before** inflate — never the reverse.
  2. Tighten floor (a **retained-memory guarantee**) ≥ **touched** + 512 MB, or a per-sandbox peak profile; never a thin constant. **`touched` is defined as the sandbox's resident anonymous working set — `AnonPages` from the guest-agent heartbeat (MB), the non-reclaimable pages the balloon must preserve; page cache is excluded by construction because it is re-faultable** (the heartbeat already carries `anon` alongside `avail`/`cached`, X5 prototype). The balloon amount actually PATCHed is `cap − floor` — Firecracker's `amount_mib` is memory *removed* from the guest, not memory retained, so sending the floor value directly would invert the rule. The floor is **cap-bounded**: when `touched + margin` would reach or exceed the sandbox's cap (a small-cap guest with a large working set), the tier **skips** that sandbox — no balloon action, recorded for observability — rather than executing an infeasible inflate. (The measured 512 MB margin comes from the ≥2 GiB-cap elastic profile; page-cache squeeze is a separate, lower-risk path with its own touched-relative margin.)
  3. Freeze new inflates before global tighten (429 + `Retry-After` on the existing retryable mapping; the prototype used 409), tighten before any consideration of eviction — and eviction remains out of scope (see Non-Goals); the degradation mode of the red line is "sandboxes run slower", not "sandboxes die".
- **Complementary, not competing, with snapshot policy (E10):** reclaim reduces *memory* pressure; dirty-rate-aware differential snapshots reduce *storage* pressure (the actual first wall, E2). The two layers share one measured input — the dirty-page ratio — and one escape hatch (below). Batch pause/restore cohorts additionally need rate shaping to avoid write storms; we documented that problem shape separately ([AgentENV #506](https://github.com/kvcache-ai/AgentENV/issues/506)) and consider it orthogonal plumbing.
- **Tradeoff.** FPR-only (no balloon) would be simpler but cannot *actively* tighten under pressure — it only harvests what guests voluntarily free. The balloon adds a control surface with real failure modes; the ordering rules and `deflate_on_oom` are how we make it safe, at the cost of a guest-agent dependency.

### Layer 3 — Observability: operating density as an SLO

- **Safety:** host-visible OOM kills per Fastlet (target: zero; a guest-internal OOM is user-visible application behavior, reported through the guest-agent event channel and *not* a host fault); red-line dwell time; misjudgment count.
- **Effectiveness:** bytes reclaimed per FPR interval and per balloon action; inflate → effective latency (~500 ms); red-line → tighten latency (6.2 ms); per-sandbox non-reclaimable residency vs total RSS (the admission feedback signal).
- **Capacity:** snapshot storage in on-disk `du` terms — alerting must use measured disk accounting, not ledger estimates: in our cache-ledger crash-recovery experiments, ledger-vs-disk drift spanning −2.91% (ghost entries over-stating usage → false alerts) to +4.43% (unregistered orphans under-stating it → missed alerts) distorted capacity alerting while the real wall was storage (E2). Pin/hot-page counts for any pinned working set, and differential-snapshot hit rate per cohort.
- **Tradeoff.** None of this needs eBPF or in-guest agents beyond the optional guest-agent; it rides cgroup stats + Firecracker API + filesystem measurement, consistent with the existing OTel instrumentation direction ([OSEP-0010](0010-opentelemetry-instrumentation.md)).

### Layer 4 — Escape hatches

- **Dirty-rate escape:** when the measured dirty-page ratio exceeds ~60% (hard fail at >95%), the snapshot path writes dense — differential snapshots never amortize at high dirtiness (E10), and a dense write is strictly cheaper than a useless delta plus a full fallback.
- **Floor guarantee:** during red-line events, queued/inflight sandboxes never drop below their declared floor (E7's 84 MB lesson).
- **`deflate_on_oom` always on** (E5): the last-resort tier that requires no policy and no signal.
- **Admission freeze with Retry-After** rather than silent queuing: callers get a machine-usable signal on the existing 429 temporary-admission-exhaustion semantics (the prototype's 409 was internal; a structured freeze-reason code is future additive work).

### Notes/Constraints/Caveats

- **Evidence is environment-spec level by intent.** All numbers in this proposal come from our own validation stack (bare-metal EPYC hosts, ~504 GiB RAM, kernel 6.8, Firecracker v1.17.0, guest kernel 6.1 with `CONFIG_VIRTIO_BALLOON` + `CONFIG_PAGE_REPORTING`, 1 vCPU / 512 MiB micro-VMs); harness details are available on request.
- **Measurement boundary.** For the evidence and all acceptance numbers: bare-metal node, single Pool, warm steady state (fleet pre-created and resident ≥ 10 min), no other tenants; cache state stated per test.

### Risks and Mitigations

- **Misjudged tightening harms a resident guest.** Mitigated by the measured ordering rules (R5) and the guaranteed floor; the acceptance tests deliberately assert the known-bad thin floor to keep the failure mode visible. Rollback trigger: any guest OOM kill during tighten → raise the floor default or disable the tighten tier (Stage 1 switch).
- **Balloon control-channel loss.** A sandbox continues running; `deflate_on_oom` stays guest-side; admission freezes conservatively. This failure mode is a named test case, not an assumed invariant.
- **Storage, not memory, is the first wall.** Density gains are only realizable if snapshot storage keeps up; the dirty-rate escape hatch (E10) and `du`-based capacity alerting (R8) are mandatory companions, not optional polish.
- **Red-line false positives.** Handled by the misjudgment counter as a first-class safety metric (Layer 3) with an explicit rollback trigger (misjudgments > 0 → disable the red-line flag); the disable path never strands capacity (see Upgrade & Migration Strategy).
- **Rollout visibility.** Every stage is flag-gated and defaulted off, and each stage's rollback is individually verified in the Test Plan; no stage changes behavior of existing sandboxes.

## Design Details

### Compatibility

As in OSEP-0026, no public OpenAPI, spec, or SDK change is involved; every surface below is fast-sandbox-internal (CRD, FastPath proto) and additive.

- **`LegacySlot` pools: bit-for-bit unchanged.** Every new signal, tier, and invariant is `ResourceAware`-scoped and flag-gated; with switches off, admission, placement, and enforcement behave exactly as today.
- **CRD/API surface: additive only, and gates live on a mutable surface.** The new knobs (red-line thresholds, invariant knob, floor/cap default tier) must be carried by a **mutable** policy surface — e.g. pool annotations or an adjacent policy object — **not** inside the immutable `SandboxPool.spec.sandboxResources` profile, whose post-create mutation fast-sandbox refuses (see [OSEP-0026](0026-resource-oversubscription-accounting-for-fast-sandbox.md) responsibility boundaries); gates placed inside it could never be switched off in place, which would void every rollback path below. `CreateSandboxRequest.resources` gains an optional floor/cap extension (additive proto). Absent fields = current semantics. Older FastPath builds ignore unknown fields as today; the OSEP-0026 recorded-shape replay is unaffected — a template's machine maps naturally to `cap`, and `floor` is new and optional.
- **Snapshots: no format change.** Balloon device state already survives save/restore (E3); FPR state likewise. Existing snapshots run unchanged; newly baked snapshots add no new device types.
- **Version skew:** elastic-tier admission requires Fastlet capability report (same gating pattern as the `RESOURCE_AWARE` mode check in OSEP-0026). A pool with elastic tier enabled on a Fastlet that doesn't report the capability falls back to limit-only admission for that Pod — never a rejected create.
- **Server surface:** the red-line freeze reuses the existing temporary-admission-exhaustion mapping — retryable 429 + `Retry-After` (the prototype used 409 internally); `Retry-After` alone is the machine-usable contract, and no public spec change is involved. Any fast-sandbox-runtime specification beyond this OSEP's scope (Fastlet admission internals, placement-filter mechanics) would live in a companion FSEP, following the pairing precedent of [OSEP-0028](0028-rootfs-only-create-overrides.md) ↔ fast-sandbox [PR #219](https://github.com/opensandbox-group/fast-sandbox/pull/219) — flagged in Open Questions.

### Flag and gating topology

| Mechanism | Gate | Scope | Default | Rollback |
|---|---|---|---|---|
| Bake hygiene (`deflate_on_oom` verify, FPR verify, metrics export) | none — bake-path property | all newly baked snapshots | on (PR #114 landed FPR) | metrics are passive; no switch needed |
| Red-line three-tier state machine (freeze → tighten → floor) | per-Fastlet flag (mutable surface) | Fastlet | off | flag off triggers a headroom-gated staged restore pass (pre-tighten balloon levels restored batch-by-batch with red-line re-checks; each batch's throttles released only after its memory is restored; insufficient headroom retains the tightened state, surfaced; control-channel-lost sandboxes surfaced); cap-sum accounting, once enabled on the pool, is retained until elastic sandboxes drain |
| Working-set admission (PSI + MemAvailable gate) | per-Pool policy (mutable surface) | Pool | off | policy off → placement reverts to ledger-only; no existing sandbox affected |
| Elastic floor/cap tier + Σ-invariant placement filter | per-Pool, capability-gated (mutable surface, outside the immutable resource profile) | Pool + Fastlet capability report | off | policy off → new creates limit-only; existing elastic sandboxes keep their already-reserved caps and the Σ-accounting filter stays active until they drain |

## Test Plan

Measurement boundary for all acceptance numbers: bare-metal node, single Pool, warm steady state (fleet pre-created and resident ≥ 10 min), no other tenants; environment class as in the Evidence section. Cache state stated per test. That single-Pool/no-tenant boundary applies to the evidence-derived numbers; the host-wide invariant tests below deliberately mix pools and add a non-sandbox baseline.

- **Unit:** Σ-invariant rejection (place until 80% cap sum, next create filtered); **host-wide accounting** (an elastic pool plus a limit-only pool plus a non-sandbox baseline charged as a bounded reservation on one host — the filter charges all three against the shared budget and blocks at it, not at the enabling pool's caps alone); aggregate-envelope check (Σ caps against the Fastlet parent cgroup `memory.max` — admission blocked or envelope resized); balloon-amount derivation (floor retained → `amount_mib = cap − floor`; never the floor value directly); floor/cap validation (floor ≤ cap, floor > 0, cap == create machine memory — a cap above the guest address space is rejected, and on restore-based creates the recorded machine is authoritative); red-line state machine transition table (normal → freeze → tighten → floor, and each reverse edge, with a normative trace for both the node branch and the Fastlet-cgroup branch); ordering enforcement (tighten plan refuses inflate-before-throttle; restore plan restores memory before releasing throttles).
- **Integration (failure coverage first):** synthetic `memhog` inside one guest during global tighten, run on the ≥2 GiB-cap elastic profile the 512 MB margin was measured on — configure both margin cases through the same `cap − floor` balloon-amount derivation: margin 512 MB (floor = touched + 512 MB; a recorded **skip** where the floor exceeds the cap) — acceptance: **zero guest OOM kills**; margin 128 MB (floor = touched + 128 MB, leaving the guest ~128 MB free after reclaiming only the 44 MB burst headroom) — acceptance: the known-bad case does OOM, keeping the regression visible; a 512 MiB-cap variant — acceptance: the tighten plan emits **skip** (no balloon action) instead of an infeasible floor; 400 MB allocation burst from a 128 MB-free guest — acceptance: survives via `deflate_on_oom` (E5); Fastlet restart mid-tighten — acceptance: sandboxes keep current balloon state, red line re-arms after restart; balloon control-channel loss — acceptance: sandbox continues, `deflate_on_oom` still guest-side, admission freezes conservatively; accounting-leak injection (ghost residency inflation) — acceptance: red line absorbs it without eviction; Stage 1 disable under low headroom — acceptance: restore batches pause and retain the tightened state instead of deflating into a refault storm.
- **E2E:** 4000 × 512 MiB steady-state soak in the red-line posture (no invariant — acceptance: 0 host OOM kills, `cpu.pressure some` held under the calibrated threshold, MemAvailable > 15%, idle residency ≤ 26 MB/sandbox + measured FPR overhead); elastic-pool invariant soak — fill to the 80% cap sum **with a co-located limit-only pool and a fixed non-sandbox baseline charged against the same budget**, then force simultaneous full inflation (deflate all balloons at once and **fault every guest's pages in to its cap — an idle deflate only exposes capacity and never makes pages resident, so the bound would not be exercised (E4)**) — acceptance: no host-level memory exhaustion and no cgroup-level OOM of VMMs (the aggregate parent-cgroup `memory.max` fits Σ caps or admission is blocked); a saturation window (busy vCPUs > physical cores) — acceptance: the CPU gate closes admission before idle-neighbor probe degradation exceeds the calibrated bound; a limit-only Fastlet driven to its aggregate cgroup budget — acceptance: the cgroup-level memory signal freezes admission before `memory.events` records VMM OOM kills; 600→4000 ramp with wall detection, extended past the predicted ~5100-sandbox storage wall or with the storage axis preconditioned/shrunk so a wall lands inside the tested range (acceptance: when a wall is hit it is storage, not CPU/memory); restore-heavy churn across the soak (FPR persistence across restore, E3).
- **Performance:** decision RTT p95 ≤ 11 ms; balloon PATCH p95 ≤ 1 ms; red-line → tighten ≤ 10 ms; inflate effective ≤ 1 s; zero admission misjudgments over a 24 h mixed-idle/busy window (including a saturation window with busy vCPUs > physical cores) at 2× the nominal memory ratio of today's defaults.
- **Compatibility:** `LegacySlot` pool behavioral regression suite (bit-for-bit); OSEP-0026 recorded-shape replay on an elastic-tier pool (template machine → cap, floor default).

## Drawbacks

- **Operational surface for pools that do not need extreme density.** Four layers, their flags, and the metrics contract exist to serve 4000-sandbox-class nodes; a small pool inherits a state machine and an observability surface it must leave off. Default-off mitigates the behavior, not the carrying cost.
- **The balloon actuator has real failure modes.** FPR-only would be simpler and dependency-free; the balloon adds a guest-agent dependency and a host-initiated control channel whose loss must be handled (covered by `deflate_on_oom` staying guest-side plus a conservative admission freeze).
- **Elasticity is create-time-only.** Firecracker cannot hot-add memory and the balloon can only shrink below the initial spec, so floor/cap cannot be resized after create — both values must be resolved up front (from pool policy and the template's machine in this OSEP).
- **The invariant trades density for the hard guarantee.** At 512 MiB caps it binds near ~800 sandboxes on a ~504 GiB node; the 4000-class idle-sparse densities in the evidence rely on the red line and get no simultaneous-full-inflation guarantee, while elastic pools that want that guarantee accept the cap-sum bound. Both postures are offered; neither claims the other's property.
- **Node-level signals are heuristics, not per-sandbox truth.** CPU `some` and MemAvailable gate safely in the measured range (E2) but cannot rank tighten candidates; making measured residency a first-class placement input remains an open question. The CPU gate's threshold is a calibration deliverable, not a measured constant, because the evidence runs never saturated CPU.

## Alternatives

- **KSM-based deduplication as the density reserve** — rejected: structurally unavailable on the snapshot-restore path this platform builds on (E6); it pays only in a fresh-boot pool form.
- **FPR-only reclaim (no balloon)** — rejected: it harvests only what guests voluntarily free and cannot actively tighten under pressure; the red-line tier needs an actuator, and `deflate_on_oom` + the ordering rules are how the actuator is made safe.
- **A combined weighted admission score (CPU + memory)** — rejected in favor of role-fixed signals: roles need no tuning surface and no hidden weights, and disagreement is resolved by construction (CPU gates density, memory gates safety).
- **Eviction, pausing, or migration as reclaim mechanisms** — out of scope (existing design-doc non-goal, kept); lifecycle automation is a separate ROADMAP row.
- **Host swap counted as node capacity** — rejected (existing non-goal, kept); a guest-side swap remains a per-sandbox emergency opt-in outside capacity accounting.
- **Dynamic overcommit-ratio auto-tuning** — rejected: ratios remain static pool policy (existing non-goal); the working-set layer reacts to pressure instead of rewriting the ledger's ratios.

## Infrastructure Needed

- **None beyond the existing surface.** Observability rides the existing OpenTelemetry direction ([OSEP-0010](0010-opentelemetry-instrumentation.md)); measurement uses cgroup stats, the Firecracker API, and filesystem measurement (`du`). No eBPF; no patched kernels beyond what fast-sandbox PR #114 already bakes; the guest-agent is optional and only required for the balloon control path.
- **Validation environment:** bare-metal Fast Sandbox nodes of the evidence class (EPYC, ~504 GiB RAM, kernel 6.8, Firecracker v1.17.0, guest kernel 6.1 with `CONFIG_VIRTIO_BALLOON` + `CONFIG_PAGE_REPORTING`); harness details available on request.

## Upgrade & Migration Strategy

Four independently flag-gated stages; each is individually disableable with no residual state.

1. **Stage 0 — bake hygiene (no runtime switch):** verify `deflate_on_oom = true` and FPR in the snapshot bake path (PR #114 landed the latter); export the Layer 3 metrics. Rollback: none needed; metrics are passive.
2. **Stage 1 — red line (per-Fastlet flag, default off):** MemAvailable < 15% three-tier state machine, ordering rules enforced. Precondition: on pools that declare caps, the Stage 3 Σ-invariant accounting must already be enabled — it is the premise that simultaneous full inflation fits, and tightening presumes it. Monitor: guest OOM kills during tighten (rollback trigger: any → raise floor default or disable tighten tier), misjudgment count (rollback trigger: > 0 → disable flag). Disable = flag off **plus a headroom-gated, staged restore pass**: restore pre-tighten balloon levels batch-by-batch, re-checking the memory red line and cgroup/node headroom between batches, and release each batch's throttles only **after** that batch's memory has been restored — a batch that cannot be restored stays throttled (throttle is the load-bearing guard for a memory-tight guest; releasing it first would recreate the OOM the ordering rules prevent). If headroom is still insufficient, the tightened state is retained and surfaced rather than deflating every guest into a refault storm (the prototype's `RESTORE_DONE`, 4.09 ms, restored a node that had already recovered — the emergency path must not assume that). A sandbox whose control channel was lost at disable time cannot be restored; it is surfaced to the operator as retained state, never silently left degraded.
3. **Stage 2 — working-set admission (per-Pool policy, default off):** PSI + MemAvailable gate new admission only. Rollback: policy off → placement reverts to ledger-only; no existing sandbox is affected.
4. **Stage 3 — elastic floor/cap tier (per-Pool, capability-gated):** create-time floor/cap, Σ-invariant placement filter. Rollback: pool policy off → new creates use limit-only, and the Σ-accounting filter **stays enabled until the pool's elastic sandboxes have drained** (it keeps counting their already-reserved caps, so those sandboxes never lose the simultaneous-full-inflation guarantee while they run). No snapshot or data migration exists in any stage; snapshots are format-identical.

Across stages, the disable path is always "policy off, keep running VMs", with two rules: the disable sequence restores pre-tighten levels in headroom-gated batches (throttles released, balloon targets restored only while headroom allows) rather than leaving sandboxes degraded or deflating into a refault storm; and once a pool has cap-sum accounting enabled and elastic sandboxes running, the Σ-invariant filter remains active until those sandboxes drain. The only residual state is a control-channel-lost sandbox that cannot be restored at disable time, which is surfaced to the operator. Everything else only constrains *new* admission and *voluntary* reclaim.

## Open Questions

1. **Companion FSEP for the fast-sandbox-native mechanics?** This OSEP is the design home for the density model, matching the ROADMAP row's "OSEP needed" marker. The mechanisms are fast-sandbox-native (Fastlet cgroups, FastPath placement, Firecracker runtime config); should their implementation-level specification live in a companion FSEP, following the pairing precedent of [OSEP-0028](0028-rootfs-only-create-overrides.md) ↔ fast-sandbox [PR #219](https://github.com/opensandbox-group/fast-sandbox/pull/219)? This OSEP would own the model, contracts, and safety properties; the FSEP would own Fastlet/FastPath mechanics. Each repository reviewing its own slice.
2. **Should measured residency become a first-class placement input?** The `ResourceAware` ledger currently exposes derived *requests* (annotations + `PoolInfo`). Admission feedback needs *measured non-reclaimable residency* per sandbox. Should that ride the existing heartbeat anti-entropy path, or the Create-response ledger snapshot — and should tighten candidates be ranked by it, or is ranking explicitly out of scope as it edges toward eviction?
3. **What happens to `maxSandboxesPerPod` on elastic pools?** The count limit is a hard control-plane boundary; the Σ-invariant is a memory-safety boundary. At 4000-sandbox-class densities the invariant binds long before any reasonable count limit. Should elastic pools treat the count limit as the control-plane ceiling only (raised, or defaulted from the invariant), or should both always bind?
